    Vorgang bearbeiten

    Frei wählbarer interner Name. Er taucht weder in Sprachantworten noch in Trigger-Erkennung auf.
    deterministic: Die gewählte Funktion wird gerendert und ihre Ausgabe direkt als Antwort gesprochen — kein LLM-Aufruf, schnell und kostengünstig. llm: Der Agent beantwortet die Anfrage frei, optional mit eigenem System-Prompt und eingeschränkten Tools. hybrid: Die Funktion sammelt zuerst die Daten, das LLM formuliert daraus eine sprechbare Antwort.
    Je Zeile eine typische Nutzerfrage, z. B. „Wie ist der Hausstatus?". Der Router erkennt auch Abweichungen (siehe Fuzzy-Schwellwert). Ohne Treffer geht die Anfrage an den allgemeinen Agenten.
    0–1, höher = strenger (z. B. 0.95 = fast wörtlich). Leer lassen = globaler Schwellwert aus den Grundeinstellungen. Typisch: 0.8–0.9.
    Gilt nur für llm/hybrid. Leer lassen, um den globalen Agent-Prompt zu verwenden. Der Platzhalter {assistant_name} wird durch den Assistenten-Namen ersetzt. Das Tool-Inventory (agent_inventory) wird weiterhin angehängt.
    Im deterministic/hybrid-Modus rendert dieser Vorgang die gewählte Funktion (ha.state, ha.call, shell + Jinja — pflegbar und testbar im Funktionen-Tab). Neue Funktionen dort anlegen, dann hier auswählen. Im reinen LLM-Modus nicht nötig.
    Angehakt = in den LLM-Modi (llm/hybrid) erlaubt; das Modell sieht dann ausschließlich diese Tools. Keins angehakt = keine Tool-Specs (Vorgang läuft ohne Tools, z. B. reine Formulierung). Gespeichert wird immer die explizite Liste. Das Template im deterministic-Modus ruft Tools unabhängig davon über ha.call auf.

    Funktionen

    Wiederverwendbare Jinja-Bausteine mit Datenabruf (ha.state, ha.call, shell). In Templates aufrufen mit {{ fn('name') }}.

    NameBeschreibungAktiv

    Funktion bearbeiten

    Der Aufrufname der Funktion. Kleingeschrieben, 2-40 Zeichen, nur a-z, 0-9 und Unterstrich. Nutzung: {{ fn('name') }} in Vorgangs-Templates oder in anderen Funktionen.
    Freitext für die Übersicht. Ab Stufe 2 wird die Beschreibung dem LLM als Tool-Beschreibung der dynamischen Funktion angezeigt.
    Wann soll der Agent diese Funktion rufen und mit welchem Ergebnis? 1-2 Saetze, evtl. 1 Beispielkommando. Beispiel: 'Nachrichten/Recherche zu jedem Thema: liefert Treffer + URLs'. Leer = Funktion erscheint nicht im Agent-Katalog (Vorgangs-Bausteine brauchen keinen Eintrag).
    Gleiches Repertoire wie Vorgangs-Templates: {{ ha.state('sensor.x') }} → Zustand einer Entität, {{ ha.entities('domain') }} → Liste einer Domain, {{ ha.call('toolname') }} → MCP-Tool ohne Argumente, {{ shell('befehl') }} → Shell im Gateway-Container (5 s Timeout, 4000 Zeichen). Jinja-Logik und Filter erlaubt. Das gerenderte Ergebnis ist der Rückgabewert der Funktion.

    Index-Quellen

    Benannte Snapshot-Indexe: Ein MCP-Tool liefert pro TTL-Fenster eine Liste, Suche/Scoring laufen lokal im RAM. Universell einsetzbar (HA-Entitäten, Music-Assistant-Player, künftige Quellen) — Templates greifen mit index.find('suche', 'key') zu, ohne Key gilt der Standard-Index.

    KeyToolTTLBeschreibung

    Index-Quelle bearbeiten

    Leer = der Standard-Index (bislang Haus). Benannte Keys werden im Template als zweites Argument angesprochen: index.find('suche', 'key') — z. B. index.find('lautsprecher küche', 'ma').
    Freitext für die Tabellen-Übersicht. Wird als „desc"-Feld im Config-JSON gespeichert und vom Index-Loader ignoriert.
    JSON mit: tool (MCP-Toolname), args (freies Argument-Objekt — beim HA-Tool steckt das Extraktions-Template im Argument), optional transform (nunjucks, JSON → Pipe-Zeilen), ttlMs (Cache-Fenster), aliases, domainHints ([{re, domains}]), stopwords. Ein weiteres benanntes System = eine weitere Zeile, kein Code.
    Rendert index.find(''[, '']) live: Ergebnis + Trace-Schritte erscheinen unter dem Editor (steht der Index gerade kalt, dauert der erste Call den TTL-Fetch lang).
